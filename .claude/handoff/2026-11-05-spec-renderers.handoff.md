# Spec renderers: component pages on the docs site first, then a Figma parity plugin

A first draft plan to render the committed ADR-027 spec files (`packages/components/src/components/<Name>/<Name>.spec.json`), plus the usage guidance in each `<Name>.metadata.json`, in two places from one shared bundle:

- **Part A:** generated component pages per spec on the Starlight docs site (`apps/docs`, ADR-022): Usage, Spec and Accessibility.
- **Part B:** a small Figma plugin that checks each component set in the main Figma file (`t4F3b1p03loOX9IpNXRaYR`) against the code contract, lists every mismatch, then draws annotated spec sheets from the same data.

Part A comes first. It's cheaper, it's public (one URL anyone can open, no Figma access needed) and it proves the bundle and the section layout before any plugin code exists. Decisions are closed and recorded in ADR-030 (see **Decisions**); build in the phases below. Facts were checked on `main` on 2026-11-05.

## Why

- **Framing: the docs are the contract.** The same `spec.json` and `metadata.json` that gate code review (`/review-component`, `spec:validate`), steer the agents that scaffold components and get checked against Figma also render the public guidelines. The pages can't drift from the component, because they're built from the file every check reads. Don't sell this as "autogenerated docs", which sounds like low-value API output. The usage guidance is written by hand, once, as structured data; only the rendering is generated.
- **Not a Storybook replacement.** Storybook stays the workshop: interactive args, every story, the a11y addon, visual regression. The docs pages are the reference layer that M3 and Carbon publish and that Storybook Autodocs doesn't cover: when to use it, what each variant is for, don'ts, anatomy, tokens. Each links to the other.
- **Why the docs site first:** the site builds from the repo already, but publishes only the reference pages and ADRs (loader pattern in `apps/docs/src/content.config.ts`). No component pages exist. Adding them is incremental work on a pipeline that's already deployed.
- **Why a plugin after that:** the public repo has no standalone Figma tooling yet. All Figma work goes through `/figma-cli` (third-party) or MCP snapshots. A parity check in Figma catches design–code drift where designers work, which neither Code Connect nor the Figma → spec tools do (positioning table in Part B). Reference point: [Spectacular](https://spectacular.systems/) goes Figma → spec, extracting anatomy, props, layout, styling and modes into schema-valid YAML/Markdown deterministically. This plugin is the reverse and much smaller: repo contract → Figma, checked. That matches ADR-002's code-first direction, and it's the only direction plan limits leave open: the Variables REST API and Code Connect are Enterprise/Org-only. The Plugin API isn't plan-gated the same way. *Verify this in Phase B0*, especially `figma.variables` read access on the current plan.
- **Consistent with the system's rules:** no AI calls (both are deterministic renderers), no live API calls (specs are bundled at build time, see "frozen-file handoffs" in `CLAUDE.md`), no new always-on automation.

| [GOV.UK](https://design-system.service.gov.uk/components/button/) | One page: when to use, how it works, one section per variant, research, recent changes | None; examples carry it |
| M3, Atlassian, Spectrum (from memory, pages didn't load) | M3: Overview / Specs / Guidelines / Accessibility, each its own URL. Atlassian: Examples / Code / Usage. Spectrum: one long page | M3: anatomy in Guidelines, measurements in Specs |
| Nathan Curtis, [Component Specifications](https://nathanacurtis.substack.com/p/component-specifications-1492ca4c94c) | Keep the spec (how to build it, for engineers) apart from the guidelines (how to use it) | [EightShapes Specs plugin](https://nathanacurtis.substack.com/p/the-eightshapes-specs-figma-plugin-2892f21adc96) generates anatomy from Figma layers, with numbered markers around the edge |

What they share: pages are split by question ("should I use this, and which variant?" before "how is it built?"), accessibility gets its own section or tab because both audiences need it, and systems that care about length split into tabs or separate URLs rather than one long scroll.

### Part A: three sub-pages per component

Separate routes behind a tab bar whose tabs are links, M3-style (`/components/button/`, `/components/button/spec/`, `/components/button/accessibility/`), so each one has its own URL and table of contents and stays short (decision 10).

- **Header (on all three):** name, `component.description`, maturity `status`, links to the Storybook story, the Figma node and the spec source on GitHub, and "Generated from `<hash>`".
- **Usage** (designers first, from metadata):
  - live default example
  - when to use it (`usage.when`)
  - variants with their `purpose`, and a short "Only available in code" note for `code-only` props (`props[].figma.surface`)
  - patterns rendered as live compositions (`usage.patterns`)
  - don'ts with their reason and alternative (`usage.antiPatterns`)
  - rules from `constraints[]` with `reason` and `enforcedBy`
  - related components (`composition`)
- **Spec** (engineers first, from the spec):
  1. **Anatomy:** overlay and legend (Phase A2). Parts with name, element, role, required / `when`, `builtOn` / `builtOnProps`, and nesting from `anatomy[].parent`; each `builtOn` part links to that component's page. CardVertical (21 parts, 4 levels) is the stress test.
  2. **Props:** prop, type, options, default, and each option's `variants.*.purpose`. **No Figma property column** (decided 2026-11-10: this page is for engineers).
  3. **States:** a rendered row of states (default, hover, focus, disabled…) with their ADR-025 `kind` and trigger.
  4. **Styles and tokens:** grouped by part, collapsed by default, with only the default condition open. Per part and condition: CSS property → token path → resolved value; literals show their `reason`.
  5. **Why it's built this way:** `decisions[]`, each linked to its ADR page on the same site when it has an `adr`, then `ruledOut[]` with the reason and source for each option (decision 12). Specs without the fields show a one-line "none recorded".
  6. **Design–code parity:** a short block at the end listing `figma.divergences[]` with the decision on each. Keep it brief.
- **Site-wide footer line:** ADRs that apply to every component (ADR-025 states, ADR-026 prop vocabulary, ADR-028 focus) are linked once here, not repeated in each component's `decisions`.
- **Accessibility** (both audiences): role, ARIA attributes, keyboard interactions table, focus note (ADR-028), the a11y tier and which test covers it.

## Part A: component pages on the docs site

### How it fits ADR-022

- Today the `docs` collection loads markdown from the repo-root `docs/` folder through `glob()`, and the sidebar is derived from filenames in `astro.config.mjs` (`pagesIn`). Nothing is hand-maintained.
- **Leaning:** render component pages straight from the bundle, with no generated markdown files to commit or keep in sync. That's either a second content collection with a custom loader over `specs.bundle.json`, or a dynamic route (`src/pages/components/[name].astro`) using Starlight's `StarlightPage` so pages keep the site chrome. Add a "Components" sidebar group derived from the bundle, the same way `referencePages` is derived from filenames.
- `docs-build.yml` only triggers on `docs/**` and `apps/docs/**`. Add `packages/components/src/components/**/*.spec.json` and the bundle script so a spec change rebuilds the site on its PR.
- These pages aren't `docs/NN-*.md` reference pages, so they sit outside `docs-check` and `/docs-sync`, like the splash page (ADR-022 amendment 2026-09-23). They can't go stale; they're rebuilt from the spec.

### Phase A1: Button and CardVertical, three sub-pages as tables

- **Routes:** one file, `apps/docs/src/pages/components/[name]/[[tab]].astro`. `getStaticPaths()` returns three entries per component from the bundle: Usage at the bare URL, then `spec` and `accessibility`. Each renders through `StarlightPage`, so the site chrome and nav stay, and passes its own `headings` for the table of contents.
- **Tab bar:** one small Astro component shared by all three pages, with each tab a link and `aria-current="page"` on the active one (decision 10).
- **Sidebar:** a "Components" group with one entry per component, pointing at Usage; the tab bar handles the other two pages. **Check:** whether Starlight's sidebar still highlights the component on `/components/<name>/spec/` and `/accessibility/`. If it doesn't by default, fix it with a small sidebar override and record which.
- Live examples, rendered states and the anatomy overlay wait for A2. A1 uses tables and text only.
- **Done when:** all six pages build on the PR check, each tab has a URL you can link to directly, the sidebar highlight works on all three routes, every row traces to a field in the spec or the metadata, and pages pass the site's existing light/dark and keyboard checks.

### Phase A2: anatomy diagram and live examples

The `@astrojs/react` setup from the spike below also covers Usage's live default example and patterns, and Spec's rendered states.

Target look: numbered markers on the rendered component plus a numbered legend, as in the [M3 card guidelines](https://m3.material.io/components/cards/guidelines). Those images look hand-exported from Figma, so they show the look, not a way to generate it. Spectacular draws on the Figma canvas from named layers, which is Part B's method, not Part A's.

**Options (checked 2026-11-10):**

- **Live component with an SVG overlay (leaning).** The page renders the real component at build time with `@astrojs/react` (the only new dependency). A small script on the page measures each part's position and size and draws numbered markers in an SVG over it. The legend comes from `anatomy[]`. It follows theme and brand, and can't drift from code because it *is* the code. No diagram library.
- **Screenshot at build time.** Playwright opens the Storybook story, reads each part's position and size, and writes an SVG with the screenshot embedded. Works without JavaScript, but needs one image per theme and makes the build heavier. Fallback only.
- **Mermaid tree** (`astro-mermaid` already installed). Shows how parts nest, not where they sit. Use it next to the overlay for deep nesting (CardVertical, 4 levels), not instead of it.

**Prerequisite: no component marks its parts in the rendered HTML** (decision 9). On 2026-11-10, no component under `packages/components/src` set `data-part`, `data-slot` or anything like it. The spec names the parts, and Figma layer names point to them (ADR-023). Code has no equivalent, so the overlay has nothing to find. This is a missing implementation convention, not a missing contract layer: `spec.json` already holds the structure the diagram needs.

- Button's `Label` is bare text with no wrapping element. Either wrap it, or measure the text node with a DOM `Range`.
- Optional parts with a `when` condition (Button's `Icon`, `TrailingIcon`) render only with the right props. The diagram needs a set of props that turns them all on. That could be an optional spec field or a dedicated Storybook story.

**Spike:**

1. Add `@astrojs/react` to `apps/docs` and confirm a component renders inside Starlight with its CSS Modules and `tokens.css`.
2. Add `data-part` to Button and CardVertical only, and build the overlay.
3. Check whether CardVertical's 21 markers still read clearly. If they don't, fall back to a Mermaid tree plus markers on the top-level parts only. Record which one ships.

## Part B: Figma parity plugin

**What it is:** a design–code parity checker that runs in Figma on a Pro plan. It checks each component set in the main file against the code contract (the bundle) and lists every mismatch. Spec sheets on the canvas come second, as the readable output of the same data.

**Positioning (researched 2026-11-10):**

| Tool | Direction | Answers |
|---|---|---|
| Code Connect | Figma → code | "What code do I write for this?" Links the two sides in Dev Mode; never checks that they agree. Org/Enterprise only. |
| EightShapes Specs, Spectacular | Figma → spec | "What is this made of?" Anatomy, props and spacing drawn or extracted from Figma. |
| This plugin | code → Figma, checked | "Does this Figma component still match the code contract?" |

It complements Code Connect rather than competing with it: Code Connect tells a designer what code to write; this tells the team whether the Figma component still matches the code. On its own, drawing sheets would read as a copy of EightShapes Specs, so sheets come after the check. Portfolio value: Plugin API depth (variables, `boundVariables`, component properties), governance as checks rather than more docs, and a measured known-answer result.

**How it fits the system:**

- The bundle is compiled into the plugin at build time (esbuild JSON import), so the plugin makes no network calls.
- Results leave Figma as a downloaded `figma-parity.json` that Facundo commits. It becomes a frozen snapshot that `sense.js` reads, so Figma drift shows up in `npm run status` and agent context without CI ever calling Figma (decision 11).
- Recorded `figma.divergences[]` and the representational divergences in the `figma-file-variable-drift.md` memory note are skipped, not flagged. Each skip is listed in the output, so they stay visible.

**Not in scope:** Figma → spec extraction (Spectacular's direction), publishing to Figma Community, any LLM call, Code Connect, multi-brand checks (Figma stays single-brand, ADR-012), writing to Figma in v1 (decision 7).

### Rules

Each rule reads only the bundle and the open Figma file. Every finding carries the rule, the component, the node id and name, what the contract expects and what Figma has.

| Rule | Checks | Source in the bundle |
|---|---|---|
| `token-binding` | For each `styles` entry that maps to a Figma property (padding, gap, height, width, radius, fill, stroke), the node's bound variable equals the spec token's Figma variable. Flags a different variable, or no binding at all. | `styles`, Figma variable names |
| `prop-coverage` | Spec props with a `figma.property` exist on the component set with the same options; props and variants in Figma that aren't in the spec are flagged too. | `props[].figma` |
| `part-names` | Each `anatomy[].name` exists as a layer name in the default variant (ADR-023). Turns B0's one-off check into a permanent rule. | `anatomy` |
| `stale-sheet` | A generated sheet's stored hash equals the bundle's hash for that component. | per-component hash |

### Phase B3: spec sheets with anatomy markers

The readable output, drawn after the check exists. One auto-layout frame per component, placed next to its component set (`figma.sets[].nodeId`) or on a Specs page (decision 6). Styled with the UpSkill library's own text styles and variables, so the docs are built with the system they document. Part A's pages are the reference for wording.

1. **Anatomy.** An instance of the default variant with numbered markers on each layer matching an anatomy part, plus the legend. A part with no matching layer shows as "not found in Figma" (the same result as `part-names`), never skipped.
2. **Props.** Prop, type, options, default, Figma surface and property. `code-only` props are shown and labelled, not hidden, because that's what designers usually lack. The Figma columns belong here, not on the web.
3. **Styles and tokens.** Per part and condition: CSS property → token path → resolved value, with redlines on the instance (padding, gap, height, radius) labelled with the token. Literals show their `reason`. Rows with a `token-binding` finding are marked.
4. **States and accessibility.** States with their ADR-025 `kind` and trigger, role, ARIA attributes, keyboard interactions table, focus note (ADR-028).
5. **Constraints and divergences.** `constraints[]` with `reason` and `enforcedBy`, and `figma.divergences[]` with the decision on each.

- **Idempotent:** the frame carries `setPluginData('specSheet', { component, specHash, generatedAt })`. Regenerating replaces the frame and never duplicates it.
- **Done when:** running it twice on Button gives one sheet, and every row matches the Button pages from Part A. Then CardVertical, then all 27.

### Phase B4: staleness

- `stale-sheet`: each sheet's stored `specHash` compared with the bundle; stale sheets are marked on the canvas and listed in the findings panel and in `figma-parity.json`.

## Decisions (closed 2026-11-10, recorded in ADR-030)

Full reasoning and rejected options are in `docs/decisions/030-spec-renderers.md`. Summary:

1. **ADR scope:** one ADR (030), amended when Part B starts.
2. **Docs pages:** dynamic `StarlightPage` routes, one `apps/docs/src/pages/components/[name]/[[tab]].astro`; no generated markdown committed.
3. **Anatomy diagram:** live component with an SVG overlay, confirmed or replaced by the Phase A2 spike (Mermaid tree + top-level markers is the fallback).
4. **Bundle:** built in CI, not committed.
5. **Plugin workspace:** `apps/figma-parity`.
6. **Sheets:** a dedicated Specs page in the Figma file, linking back to each set.
7. **Mismatch policy:** flag-only in v1; a per-finding "bind to spec token" action is a v2 candidate.
8. **Name:** "Figma parity" (working name).
9. **Part names in rendered HTML:** `data-part="<anatomy name>"` on each part's element.
   - **Value:** the exact `anatomy[].name`, PascalCase (`data-part="TrailingIcon"`), not Ark's kebab-case (`item-trigger`). The same string then matches in spec, code and Figma layer names, and the test is a plain string comparison. The attribute itself stays `data-part` because HTML only treats `data-*` attributes as custom data; React passes them through unchanged.
   - **Enforcement:** a render test that fails when a declared part doesn't render.
   - **Bare-text parts** (Button's `Label`) are wrapped in an element.
   - **Optional parts** are turned on by a new optional spec field, `anatomyExamples` (named at the schema step, 2026-11-10; ADR-027 and ADR-030 amendments).
     - **Props alone don't cover compound components** (ADR-023). Button's parts appear through props, but CardVertical's parts appear because someone writes them in JSX, like Ark/Chakra, where the anatomy is a composition snippet. So the field holds either example props or a reference to an existing metadata pattern (e.g. `{ "pattern": "instructor-row" }`), never a second copy of a tree.
     - **Make it a list.** Some parts can't appear together: CardVertical's `Action` holds `Favorite` *or* `Menu`, never both. Each entry is one example; the overlay and the render test cover the union, and a part missing from every entry fails the test. Scan all 27 specs' `when` conditions and `slot` parts before locking the schema.
     - **Not renderable by any example** (found in the 27-spec scan, left to the render-test step): CardVertical's `MenuPanel` (only after the menu opens; `Menu` has no `open` prop) and TextField's `Placeholder` (`::placeholder`, no element to mark).
   - **Recording:** the ADR-027 amendment and the `packages/components/AGENTS.md` line ship with the schema change.
10. **Page layout:** link tabs over three routes, `aria-current="page"`; Usage before Spec, accessibility on its own, no Figma columns on the web.
11. **`figma-parity.json`:** `.claude/figma-parity.json`, added to the frozen-snapshot table in `CLAUDE.md` when it lands; `npm run status` warns when the capture is older than the last spec change.
12. **Per-component decisions:** adopted as proposed.
    - Two optional spec fields: `decisions[]` (`{ decision, reason?, adr? }`) and `ruledOut[]` (`{ option, reason, source? }`).
    - `spec:validate` checks that every `adr` resolves.
    - Backfilled by hand, Button and CardVertical first; no `TODO` placeholders, since they fail `spec:validate`.
    - Kept out of `/component-scaffold`'s context.
    - Amends ADR-027 when the schema changes.

## Follow-up outside Parts A and B: decisions as agent memory

After decision 12 lands, close the loop with the agentic moments:
